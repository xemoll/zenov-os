# ZenovOS 0.1.1 VM Image 2

**Published:** 31 July 2026 UTC  
**Tag:** [`v0.1.1-vm2`](https://github.com/xemoll/zenov-os/releases/tag/v0.1.1-vm2)  
**Source commit:** [`d60cf00f67bc07f00070a56b237843bc8387866f`](https://github.com/xemoll/zenov-os/commit/d60cf00f67bc07f00070a56b237843bc8387866f)  
**Target:** legacy BIOS, 32-bit x86 virtual machines

VM Image 2 is the persistent multi-hypervisor ZenovOS distribution. It boots from a verified read-only ISO 9660 / El Torito optical image and stores files, settings, packages, security state and audit data on a separate writable ZenovFS disk.

The release was published separately from the immutable original `v0.1.1` and the earlier `v0.1.1-vm1` ISO release. Its tag is pinned to the exact source commit above.

## Required VM configuration

- 32-bit x86 guest;
- legacy BIOS firmware, not EFI/UEFI;
- 64 MiB RAM;
- one CPU;
- ISO attached as an IDE CD/DVD drive and first in boot order;
- exactly one writable ZenovOS data disk attached as the primary IDE disk;
- networking disabled because ZenovOS 0.1.1 has no network stack.

The ISO is read-only. Back up the writable disk while the VM is powered off. Resetting or replacing that disk destroys files and configuration created inside ZenovOS.

## Reproducibility boundary

The ISO, canonical raw images, scripts, documentation and manifests are deterministic. QCOW2, VDI and VMDK container metadata can include format-specific identifiers generated by `qemu-img`; byte-identical container files are therefore not claimed across unrelated tool builds.

The proven boundary is the guest-visible disk content. Every convenience container must convert back to the canonical raw ZenovFS image byte-for-byte before guest mutation.

## Current limitations

- live BIOS boot rather than installation of a bootloader onto the virtual hard disk;
- no UEFI boot;
- no physical-hardware installer;
- no networking, audio, guest additions/tools or accelerated 3D;
- QEMU is the automated runtime acceptance target;
- VirtualBox and VMware assets are structurally and semantically verified, but those proprietary hypervisors are not executed in GitHub-hosted CI.
